# Fleet 클라이언트 준비 (0.9.60)

> **0.9.61 추가:** 현 서버의 비동기 큐 계약에 맞춘 별도 통신부·암호화 토큰 저장소를 사전 구현했다.
> 상세 명세·연결 지점은 [FLEET_QUEUE_PREP.md](FLEET_QUEUE_PREP.md)를 따른다.
> 현재 서버에는 개폐·깨우기·취소 API가 없어 아래의 기존 wake 흐름에 직접 연결하면 안 된다.
> 아래는 0.9.60 당시의 내부 설계이며, 새 통신부도 아직 설정/서비스에 연결하지 않았다.

- 수신 서버: `https://tesla.choondoggy.com`.
- **HTTP 경로·인증·요청/응답 스키마는 미정이다. 실제 서버에 접근하지 않았다.**
- `FleetApi`는 앱 내부 계약일 뿐 서버 API 스펙이 아니다. 현재 `UnconfiguredFleetApi`로 실제 전송을 차단한다.
- 설정 → 자동화 → 음성 명령 전송 → Fleet API 사용. 기본 OFF, 저장·복원 지원.
- ON이면 음성/런처의 단일 차량 명령만 Fleet 경로를 사용한다. 앱 직접 조작·자동 매크로·폴링은 기존 BLE 유지.
- Fleet 선택 중 음성 매크로 실행은 미지원으로 종료한다. BLE로 자동 전환하지 않는다.
- 준비 중 ON으로 설정하면 음성/바로가기 차량 명령은 실행되지 않는다. 설정 화면에 이 제한을 명시한다.

## 구현된 흐름

`MacroService → FleetCommandClient → FleetApi`

1. 기존 `CommandDeadline`으로 수신부터 유효시간을 적용한다.
2. 차량 상태를 조회해 온라인이면 바로 전송 단계로 간다.
3. 수면/오프라인이면 깨우기를 한 번 요청하고 1초 간격으로 온라인 여부만 확인한다.
4. 깨우는 동안 앱 상단 취소 버튼을 유지한다. 취소 후 늦은 응답이 와도 개폐 명령을 보내지 않는다.
5. 온라인 확인 후 취소·만료를 다시 검사하고 전송 진입을 원자적으로 확정한다.
6. 요청 ID·차량·명령·남은 수명을 전달해 한 번만 제출한다. 거절/결과 미확인/통신 실패는 재전송하지 않는다.
7. 차량 성공 응답(Confirmed)만 효과음 대상으로 인정한다. 서버 접수·깨우기 성공만으로 완료음을 내지 않는다.

## 서버 계약을 받을 때 필요한 정보

- 앱 인증 방식·갱신·로그아웃, 차량 식별 방식. Tesla 장기 토큰/개인키는 앱 코드에 넣지 않는다.
- 상태 조회·깨우기·명령 제출의 실제 경로, HTTP 메서드, 요청/응답 예시와 오류 코드.
- 수면/오프라인/온라인 및 차량 성공/거절/접수만 됨/결과 미확인의 명확한 구분.
- 요청 ID 중복 방지와 **남은 수명 만료 후 실행 금지**. 서버가 명령을 큐에 넣는다면 서버 측 취소 계약도 별도 필요하다.
- 개폐 명령의 P단 확인 등 차량 안전 조건과 모델별 지원은 서버에서도 지켜야 한다.
- HTTP 어댑터는 명령 자동 재시도·다른 호스트 리다이렉트를 금지하고, 취소와 유효시간을 네트워크 타임아웃까지 전파한다.
- 계약 수신 후 어댑터 구현 → 인증/차량 오류 테스트 → 실서버 승인된 검증 → 실차 확인이 남는다.

## 효과음

- `SwitchingVehicleGateway.send`의 실차 성공 및 Fleet `Confirmed`에서 `CommandFeedback.confirmed`를 공유한다.
- 보닛/트렁크 열기·트렁크 닫기·잠금/해제·창문 환기/닫기·충전구 개폐 성공에 짧은 확인음.
- 공조/시트/충전 전류 자동 변경·폴링·거절·취소·만료·결과 미확인·시뮬레이터는 무음.
- 단말의 알림 음량·무음/진동·방해금지 설정을 존중한다. 오디오 실패는 차량 명령 재실행 사유가 아니다.
- 확인음은 **차량 성공 응답** 의미이며 물리적으로 끝까지 열렸다는 센서 확인음이 아니다.
- 차량/네트워크 없이 모형 단위 테스트를 완료하며 실차 실행과 실제 스피커 출력은 미확인으로 남긴다.
