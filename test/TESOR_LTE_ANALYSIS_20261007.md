# Tesor LTE 동작 경로 정적 분석

## 결론

Tesor 6.0b4l에는 Android 무선 디버깅(TLS/mDNS)으로 초기 연결한 뒤 `tcpip:<port>`를 보내 일반 TCP ADB를 활성화하고, 이후 시스템 속성의 포트로 로컬 재접속하는 경로가 있다.
보조 프로세스를 유지하기만 한다는 앞선 추정은 불충분했다.
Smart Tesla에는 이 TCP 전환·포트 재사용 경로가 없으며, 셸 서버를 재사용하지 못하면 무선 디버깅 포트를 다시 탐색한다.
이 차이가 Wi-Fi에 연결하지 않은 LTE 사용 중 복구 가능성의 핵심이다. 제공된 기기에서 TCP 경로를 실제로 사용했는지까지 확인한 것은 아니다.

## 확인한 호출 흐름

| 단계 | Tesor 코드 근거 | 확인된 동작 |
|---|---|---|
| TCP 포트 확인 | `ha0.java:211–229` | `service.adb.tcp.port`, 없으면 `persist.adb.tcp.port`를 조회. 0은 미사용 처리 |
| 초기 무선 연결 | `ha0.java:478–535` | `WRITE_SECURE_SETTINGS`와 Wi-Fi 연결 검사 후 `adb_wifi_enabled=1`, `adb_enabled=1`, `adb_allowed_connection_time=0`, `_adb-tls-connect._tcp` 탐색 |
| TCP 모드 전환 | `ha0.java:574–585`, `o000ooO0.java:146–149` | 설정 분기에 따라 5555 또는 임시 빈 포트를 선택하고 ADB 서비스 요청 `tcpip:<port>` 전송 |
| 임시 포트 선택 | `pe2.java:1077–1096` | `ServerSocket(0)`으로 빈 포트를 얻은 뒤 소켓 닫음. 항상 5555라고 단정하면 안 됨 |
| 실행·재접속 | `ha0.java:989–1100` | 살아 있는 클라이언트 재사용. 없으면 TCP 포트 확인, 필요 시 권한 검사 후 `adb_enabled=1`, 저장된 인증 자료를 사용하는 클라이언트로 `127.0.0.1:<port>` 접속 |
| TCP 포트 없음 | `ha0.java:999–1015` | 초기 mDNS 준비 함수로 돌아감. 초기 준비·재부팅 이후까지 항상 Wi-Fi 불필요한 구조는 아님 |
| 명령 호출자 | `ha0.java:810–844`, `868–901` | 클라이언트가 없으면 위 재접속 함수를 호출한 다음 명령 처리 경로로 진행 |
| 종료 정책 | `ha0.java:1213–1276` | 설정 분기에 따라 ADB 유지 또는 무선·USB 디버깅 해제. 무조건 상시 켜두는 방식은 아님 |

`127.0.0.1`은 클라이언트 접속 대상이다. 이 사실만으로 ADB 서버의 수신 범위도 루프백으로 제한된다고 판단할 수는 없다.
여기서 확인한 것은 디컴파일된 제어 흐름과 해독된 상수이며, 기기별 TCP ADB 허용 여부·종료 후 속성 유지·재부팅 복구는 실행 검증하지 않았다.

## 수정 전 Smart Tesla와 로그에 대입

- `WirelessNavigation.kt:143`의 `ensurePrepared()`는 무선 디버깅 활성화를 먼저 요구하고 기존 Binder 서버를 검사한다.
- 서버 재사용에 실패하면 `LocalAdbDiscovery.port()`의 무선 디버깅 NSD 탐색과 저장된 무선 포트로 연결한다. Tesor의 `service.adb.tcp.port` 조회·`tcpip:` 전환에 대응하는 단계는 없다.
- 사용자 로그의 20:36에는 기존 서버 버전 확인 뒤 티맵 실행 요청과 메인 Activity 진입이 관측됐다.
- 20:50에는 채널 IOException·종료 확인 실패, 22:57에는 기존 서버 확인 없이 연결 포트 탐색·갱신 대기 후 약 30초 만에 실패했다.
- 따라서 LTE 인터넷 장애로 단정할 수 없다. 기존 제어 경로를 재사용하지 못했을 때 Wi-Fi 포트 탐색에 의존하는 복구 한계와 일치한다. 기존 프로세스가 왜 사라졌거나 접근 불가능해졌는지는 로그만으로 확정할 수 없다.

## 적용 판단

재사용 가능한 개념은 최초 인증과 일상 재접속을 분리하고, 인증된 로컬 TCP ADB를 복구 경로로 활용하는 것이다.
단순 재시도 횟수 증가나 보조 프로세스 유지 보완만으로 Tesor와 같은 복구 경로가 생기지는 않는다.
우리 앱은 현재 USB 디버깅을 자동 변경하지 않으므로, Tesor의 전역 설정 변경·인증 유효시간 무제한·포트 정책을 그대로 복제하는 것은 동일 범위의 작은 수정이 아니다.
실제 적용은 인증 유지, 포트 수신 범위, 기존 ADB 사용과의 충돌, 재부팅 및 ADB 불가 경로를 검증하는 별도 구현이 필요하다. 최초 분석 시점에는 코드에 적용하지 않았다. 이후 사용자의 추천방향 진행 승인으로 구현·검증을 이어갔다. 최종 결과는 `LTE_RECOVERY_20261007.md`를 참고한다.
